2026-09-02 MOC 地图层大规模冷启动（从 0 建 11+ MOC、归档 8 个旧 MOC）踩出 7 个坑，现有 jfox-moc skill 只覆盖单 MOC 的 diagnose → create → update 生命周期，批量建设与成员质量治理无覆盖。目标：把 7 条增量经验补进 skill，下次整理 MOC 不再重踩。

调研结论（详见 research/01-kb-issues-code-survey.md）：7 条全部有据可依，无阻断。

**组织方式（已确认）**：混合——通用规则上提到现有 Step 1-3/关键原则（单一来源），新增「批量建设与成员质量审查」章节给冷启动场景完整流程线，章节内引用不复述。

## 通用规则上提（嵌入现有章节）

| 位置 | 上提内容 | issue 条目 |
|---|---|---|
| Step 1 诊断 | 簇序号时效性：seed=42 只保证同一库状态下可复现；库变动（新建/归档 MOC、改标题）后 Louvain 重跑序号失效。每次 create 前重新 diagnose，用 hub 标题确认目标簇，不认旧序号（实测：差点把 CR 簇当 skill 簇建） | 5 |
| Step 2 草稿与确认 | 审成员时效性：草稿生成后先读成员笔记全文，识别失效/过时笔记，先归档/更新再落盘（实测：双 bot 时代笔记在单 bot 化后已失效，直接建 MOC 会固化过时结论） | 1 |
| Step 3 落盘 | 管道语法铁律：MOC 正文一律 `[[ID\|标题]]`，一条规则挡两个坑——同名标题歧义（session-to-permanent 重复产出主因）+ 标题含 `#` 锚点截断静默丢成员（实测丢 #158/#195）。**操作后果（#458 修复前）**：`moc create` 产物正文仍是 `[[标题]]`，落盘时必须人工检查成员清单，把标题含 `#` 或同名风险的成员改写为 `[[ID\|标题]]` 再 `--yes`。标注：#458 修复 draft.py 渲染后 moc create 产物自动免疫，手写正文仍须遵守 | 3、4 |

## 新章节「批量建设与成员质量审查（冷启动/重构）」——置于 Step 4 之后、「关键原则」之前

1. **适用场景**：从 0 建多个 MOC / 大规模重构现有地图层
2. **批量主流程**：批量 diagnose → 逐簇 dry-run + 审时效性（引用 Step 2 规则）→ 落盘（引用 Step 3 管道铁律）→ 覆盖度核查 →（可选）合并/归档
3. **手动建 MOC 路径**（无独立簇时）：关键词搜索收集 → 与现有 MOC 成员差集排除 → 分组呈现 → 用户确认 → `jfox add --type structure --tag moc` 落盘。标注：#484 落地后可简化；此前有 #470 风险（edit 覆盖 frontmatter links 不去重），正文 wiki-links 与 frontmatter links 需同步维护。手动 MOC 与 create 产物同受 `moc update` 管理（按 type=structure 扫描，代码已确认）
4. **覆盖度核查**：建完后关键词搜索 + MOC 成员差集捡漏（实测：CR MOC 初版漏 16 条，含 2 条核心根笔记）。附 bonus 坑：`jfox list --type structure` 默认 limit 10 会漏 MOC，`--limit 20` 起步
5. **合并/归档处置**：旧 MOC 无意义 → `jfox archive`（structure 归档不影响成员笔记；实测 8-27 测试批次 7 个 MOC 全归档）；主题重叠 → 合并（实测：TUI MOC 并入 pi-agent-board 大 MOC）
