# 设计文档：重构 permanent 笔记模板（稳定核 + 类型段 + 易变细节）

- **Issue**: zhuxixi/jfox #375
- **类型**: refactor(skill) — 纯文档改动（skill 散文层模板），不碰任何 `.py`、不触发 CI
- **日期**: 2026-08-11
- **方案**: A — 单骨架 + 可选类型段

## 1. 背景与问题

`jfox-session-to-permanent` Step 3 的模板是固定三段式（一句话 / `## Why` / `## How to apply`），按「方法论笔记」设计。但 KB 里约 3/4 的 permanent 是现状快照 / 机制原理 / 自动化链路类，标题与内容对不上。

调研（见 `research/` 两份）确认根因：这些「现状」类笔记在经典 Zettelkasten 里其实是 **project note / status snapshot**（Ahrens：活在 slip-box 之外、绑特定项目、有时限），不是「概念」。《活文档》本质就是 project note 的现代软件工程版，所以对这批笔记精准命中；但 KB 里也有真概念笔记（Zettel），活文档框架对它们不合身。结论：模板必须**同时服务 project 类和概念类**两种血统的笔记，不能只按一种设计。

## 2. 目标 / 非目标

**目标**
- 用一套骨架服务现状 / 机制 / 链路 / 概念 / 方法五类笔记，类型段按内容选标题。
- 把「易变的实现细节」（路径/版本/端口）与「稳定的核」（结论+依据）显式分层。
- 三平台 skill（pi / cc / kimi）的模板 body 文字逐字一致。

**非目标**
- 不回填历史 permanent 笔记（仅对新沉淀生效）。
- 不引入 MOC / structure note 层（那是 `jfox-organize` 或独立 skill 的范畴，本 issue 只管单条笔记内部结构）。
- 不改 `jfox-promote`（调研确认它不引用本模板）。
- 不改 Step 1/2/4/5（提取/去重/审阅/落库）——只改 Step 3 的「内容结构」块及其紧邻说明。

## 3. 核心设计

### 3.1 新模板（替换三段式）

Step 3 现有的「**内容结构**（事实 → Why → How to apply）」整块（含其下 code block）替换为下面这版「**内容结构**（稳定核 + 类型段 + 易变细节）」+ 紧跟的「类型段目录」表：

````markdown
**内容结构**（稳定核 + 类型段 + 易变细节）：

```markdown
<一句话结论。这条笔记最稳定、最值得未来记住的那句话，开门见山放第一句。>

## 为什么（背景与依据）
<这条知识回答的是什么问题；成立的前提/约束/假设。
 若是决策类：写当时的背景、选它的主要原因、以及认真考虑过但没选的替代方案——依据很大程度上在于"被丢弃的选项"。
 没东西可写就整段省略，别硬凑。>

## <类型段，选 0–1 个，标题写实>
<按笔记内容从下方"类型段目录"选一个标题，或整段省略。>

## 怎么用
<什么场景下用、具体步骤或命令。结合示例或命令。>
```
````

> **易变细节处理（写作指导，不是每条笔记的固定段）**：路径、版本号、端口、文件位置归到「## 怎么用」，它们是易变的"实现决策"，核（结论 + 为什么）不写具体值、保持常青。**只有当「## 怎么用」里确实出现了这类易变值时**，才在该段末尾加**一句具体的**核对提醒（如「端口以 docker-compose.yml 为准」「路径以实际仓库为准」）；没出现就不加。理由见《写作的逻辑》p131/132：固定的模板话重复进每条笔记会掩盖该条自己的重点，违反简洁。

**新模板相对旧三段式的 3 个关键区别**：

1. **类型段标题写实**——机制类写「## 它怎么工作」、现状类写「## 当前现状」，不再硬塞进 Why。解决 3/4 笔记的失配。
2. **「为什么」可省略**——现状类没背景依据可写时整段不要，不再凑假 why。概念/决策类才写，且决策类要含被丢弃的替代方案。依据《写作的逻辑》p80「短篇可省略结论，因总论有等价内容」。
3. **易变细节归到「怎么用」**——路径/版本/端口进「## 怎么用」，核（结论+依据）不含具体值、保持常青；只在真出现易变值时加一句具体核对提醒，不贴固定模板话。符合活文档「策略（核）与实现（易变值）分开」+《写作的逻辑》简洁原则。

### 3.2 类型段目录（紧跟模板 code block 的新增表）

**选标题的原则**（《写作的逻辑》p110）：标题要**写实、具体**——写这条笔记实际在讲的主题，不套抽象类别名；**一段一个主题，不用「A与B」复合标题**（如不要「运行速度与耗电量」，要拆成两段或选其中一个）。下表是常见内容类型的推荐标题，不是固定菜单——内容不属于下表任何一类时，按「写实」原则自己起一个具体标题。

表上方一句结论句（遵循 clear-reports「表上方给结论」）：**类型段按笔记内容选 0–1 个标题；方法/调试类通常省略，直接并进「怎么用」。**

| 笔记内容 | 类型段标题 | 这一段写什么 | 血统 |
|---|---|---|---|
| 机制 / 原理 | `## 它怎么工作` | 系统/工具的运作机制、各部分如何配合 | project/system 类（活文档框架） |
| 现状快照 | `## 当前现状` | 脚本/文件/端口/配置的当前位置与状态 | project/status 类（活文档框架） |
| 自动化链路 | `## 链路与组件` | 多组件串联的链路与各组件职责 | project/system 类（活文档框架） |
| 纯概念 | `## 概念` | 可复用的概念、原理、术语解释 | 经典 Zettel 永久概念类 |
| 方法 / 调试 | （省略） | 直接写进「## 怎么用」 | — |

> 「血统」列**不写进 skill 正文**（那是给设计者看的理论依据），只在本 spec 保留。skill 正文里这列去掉，保留前三列。

> **链路类的特殊提示**（写进 skill 正文，类型段目录下方一句）：一条笔记若在画多个组件的关系，本质是「迷你 structure note」——组件多了应考虑拆成一个 MOC + 各组件独立笔记，而不是把所有组件塞进一条 fat note。

### 3.3 自检标准（写进 skill 正文，类型段目录之后）

加一段写作时自检：**把「## 怎么用」整段遮住，剩下的「结论 + 为什么 + 类型段」是否还独立成立、还有价值？是→分层成功；否→核里写进了易变细节，需要把具体路径/版本挪到「## 怎么用」。**

### 3.4 写作规范 5 条 / wiki links 段——不变

Step 3 现有的「**写作规范（遵循 clear-reports 段落写作法）**」5 条规则**逐字保留**：它们讲的是散文风格（先结论、段首概要、术语解释、完整句、表格用法），与新结构不冲突，规则 1「第一句话就是核心事实」与新模板「一句话结论」一致。

「**嵌入 wiki links**」段也**逐字保留**。

## 8. 理论依据（简）

- **活文档（Martraire）**：知识快慢之分、常青内容关注意图而非实现决策、策略文档与实现文档分离、决策依据结构（背景/问题/原因/被丢弃方案）。→ 支撑「稳定核 vs 易变细节」分层 + 「为什么」段的精确定义。对 project/system 类笔记精准。
- **Zettelkasten project note（Ahrens/Sascha）**：project note 活在 slip-box 之外、绑项目、有时限。→ 解释「现状」类为何装不下旧 Why/How，并要求模板同时服务 project 类与概念类。
- **Sascha「purpose 决定内容」**：一条笔记的目的决定它装什么。→ 类型段 = 让写作者声明 purpose，是方案 A 的理论内核；也说明为何不必走方案 B（每类一套骨架）——purpose 用选标题表达即可。
- **《写作的逻辑》（仓岛保美，书架 distill→clear-reports）**：段落写作法。→ 支撑四段壳的每一条：
  - p027「写作者有背景信息、阅读者没有，结论须先行」→ 一句话结论放第一句。
  - p080「总论要具体；短篇可省略结论，因总论有等价内容」→ 结论写实 + 为什么段可整段省略。
  - p110「每段设定具体主题、不用抽象主题、不用 A与B 复合标题」→ 类型段标题写实/一段一主题。
  - p131/132「概要句要简洁，啰唆拖沓会掩盖重点」→ 易变提醒不进每条笔记正文、只在需要时加具体一句。
  - 全书「反例 + 修改范例」教学法 + p027「按逻辑写而非感觉」→ 自检标准进 skill 正文。

## 9. 风险与降级

- **风险**：类型段「选 0–1 个」仍需作者判断，可能选错或漏选。**降级**：自检标准（§3.3）兜底——选错会导致「核不成立」，自检能发现。不强求自动判定。
- **风险**：三平台 drift。**降级**：改完三方 diff + Zima CR 多轮收敛（memory 已记录 Zima 文档严格性）。
- **风险**：新模板比旧的长（多了类型段目录 + 自检）。**接受**：清晰比简短重要（skill 现有写作规范已声明此原则）。
